# 小行星问题记录

抄它设计的时候顺手看到的。**只记录，不修** —— 那边的事留给家里那位 AI / 本人决定。
所有数字都是实测，不是感觉。

## 1. 仓库体积

| 项 | 数字 |
| --- | --- |
| `.git` | 183 MB |
| 打包产物 blob（apk-out、.gradle 缓存等） | **53 个，共 253 MB**（压缩后仍是主要体积） |
| 中断残留的临时 pack（`tmp_pack_*`、`.l2s.tmp_*`） | 37 MB |
| 工作区 `AndroidApp/app/build` | 209 MB |
| 工作区 `apk-out` | 25 MB |
| 被跟踪文件总数 | 183 个 |

`apk-out/app-debug.apk`（单文件 24–25 MB）在历史里出现十余次。
可考虑：`git filter-repo` 刮掉 `apk-out/` 和 `AndroidApp/.gradle/`，再 `git gc --prune=now` 清 tmp pack。
apk 以后只走 release / apk 分支。**注意这步会改写历史，别人克隆过的本地要重来一次，所以别急着做。**

## 2. 规则和事实打了一架

以后新增的 workflow 会被静默忽略 —— 某天"我明明加了 CI 怎么没跑"就是这儿。

## 4. 零自动化测试

没有 pytest、没有 unittest。只有 `selftest_api.py`、`inspect_context.py`、`ctxdump.py` 三个手工脚本。
1069 次提交全靠手验 —— 提交记录里一半是"真凶是它""修：xxx 不显示"，这是根源。
真要动的话，建议先只给两块加测试：**记忆检索排序** 和 **上下文组装**。这两块坏了最难发现。

## 5. 分支在当备份用

10 个分支，其中 4 个叫 `backup-before-*`（location / proot / multiroom）。
说明动大件前靠手动开分支兜底，而不是靠测试。

## 6. 前端在猜后端（它自己文档承认）

`docs/聊天上下文怎么走.md`：前端拿后端历史 + 本地缓存合并，字段名对不上，
靠 `uuid`、`date|time|content` 去猜着匹配，猜错就"重进一次多两条"。
同一份文档里还列了四条"待清理"：前端工具合并那套、死代码 `interim_reply`、
`toolSummary` 双来源、一堆补丁式去重。

它自己写了原则，我觉得是对的：**能删就删，删不了再退化；宁可少一层"猜"，也别多一层"合"。**

## 7. 数据在打架

`space.db`（消息）+ `memory.db`（记忆）+ 外部向量库；记忆库 4 张表，
外加上下文还有两套来源（`context_items` 固定项 + `context_recent` 最近项）。
四五个地方都可能"记着同一件事"，同步不上就是记错。

## 8. 做得好的（别改）

- `.env`、`providers.json`、`*.db` 都正确地被 ignore 了，没有硬编码 key（grep 过）。
- 记忆设计有观点：短标题当名字、权重衰减、重要位有限、情绪消化还重量。这是真东西。
- `memory/verify.py`、`weights.py` 这种小模块拆分是对的，只是没拆完。
